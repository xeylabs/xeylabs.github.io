Hardening Mythic.

This entry records one week of work on Mythic in one pass: two M1 roadmap items and a hardening pass driven by adversarial testing of our own server. The testing produced twelve findings; all twelve are fixed, each pinned by a regression test, and each fix was re-verified against the original reproduction before it was called done.

Key rotation without downtime (ADR-0006)

Until this week Mythic signed every decision token with a single Ed25519 key; rotating it meant a restart and invalidated every live token. The server now keeps a key ring with exactly one active signer. Rotation is time-based and runs in-process (MYTHIC_KEY_MAX_AGE, default 720h); retired keys stay advertised in the JWKS for MYTHIC_KEY_RETENTION (default 24h) — longer than any token they signed can remain valid. The keystore is a JSON file written atomically; legacy 32-byte seed files still load and migrate on first save. Origins keep verifying tokens locally, selecting the key by the kid claim.

Store: Redis for multi-node (ADR-0009)

The in-memory store bound mythicd to a single node. MYTHIC_STORE=redis selects a Redis backend: single-use challenges via GETDEL (atomic fetch-and-delete) and pressure counters as sorted sets pruned by one Lua script. Both backends implement sliding-window counters, which closes the fixed-window boundary burst. The Store interface now returns errors: an unreachable Redis refuses startup, and a runtime outage surfaces as 503 store_unavailable on /v1 while /healthz stays open for load balancers. A shared contract suite runs against both backends (memory and miniredis) so their semantics cannot drift.

One caveat in writing: the store is shared, signing keys are not. A token from node A does not verify against node B's JWKS. Multi-node token verification needs a shared keystore (KMS/HSM) — M5, not solved by this change.

Hardening pass: twelve findings

Adversarial testing — black-box against a live server, with white-box confirmation where needed — produced twelve findings. The notable ones, grouped by area:

Transport and limits

The rate-limit budget was consumed only after validation: invalid-JSON and unknown-site-key floods ran unthrottled (600 requests at 225 req/s, zero 429s). Budget is now counted before validation. The limiter keyed IPv6 at /128 — a single /64 controlled 2⁶⁴ identities (5,000 requests from one block, zero hits); counters now aggregate IPv6 to /64 (ADR-0007). No body/read/idle timeouts existed; a slow client held connections indefinitely. ReadTimeout, WriteTimeout, and IdleTimeout are set.

Challenge economics

The solve-time floor modeled a 50k H/s worker; measured crypto.subtle workers run ~400k H/s, so honest clients were flagged as implausible — and any client could simply delay verification past the floor. The floor is now a low quantile of honest solve time (2^d / (2M × 32), ADR-0008): false positives ≤ ~6% worst case, GPU-class answers trip it ~96% of the time. The threat model states that a wall-clock floor cannot catch a client that delays verification — that is the behavioral layer's job (M2).

Tokens and configuration

The documented invariant that tokens never outlive their challenge was unenforced — a 1-hour token was issued from a 5-second challenge. TokenTTL is now clamped to ChallengeTTL. Hostile tuning (MYTHIC_FAST_SOLVE_PENALTY=500) leaked a risk score of 500 into signed tokens; scores clamp to 0–100 and penalties above 100 refuse to start. A negative MYTHIC_BASE_DIFFICULTY issued challenges any nonce satisfied; configuration is validated at startup and out-of-range values refuse to serve.

State handling

Two processes sharing one keystore collided on the same temp file or silently split-brained their signing keys; temp names are process-unique and saves refuse to overwrite a file changed since load. Trailing bytes after a JSON value were silently ignored; they are rejected. The sliding-window counter stored one entry per hit — including rate-limited ones — so a million hits from one identity cost ~16.4 MB of heap and 595 s of CPU. Counters now saturate at IPLimit+1: the same flood costs +0.00 MB and 714 ms.

Verification

Every finding has a reproduction; every fix has a regression test (go test ./... -race, plus the SDK typecheck and tests), and every fix was re-verified against the original reproduction. What remains open is documented in the threat model: patient solvers that delay verification (M2, behavioral signals), distributed attacks with fresh identities (M1, network fingerprints), and per-node keystores (M5, shared KMS/HSM).
