Mythic 하드닝.

이 엔트리는 Mythic의 일주일간 작업을 한 번에 기록한다: M1 로드맵 두 항목과, 자체 서버에 대한 어버서럴 테스트가 주도한 하드닝 패스. 테스트는 12건의 발견을 냈다. 전부 수정되었고, 각각 회귀 테스트로 고정되었으며, 모든 수정은 완료 선언 전에 원래 재현 절차로 재검증되었다.

다운타임 없는 키 로테이션 (ADR-0006)

이번 주까지 Mythic은 모든 결정 토큰을 단일 Ed25519 키로 서명했다; 로테이션은 재시작을 의미했고 살아있는 모든 토큰을 무효화했다. 서버는 이제 정확히 하나의 활성 서명자를 가진 키 링을 유지한다. 로테이션은 시간 기반이며 프로세스 내에서 동작한다 (MYTHIC_KEY_MAX_AGE, 기본 720h); 은퇴한 키는 MYTHIC_KEY_RETENTION(기본 24h) 동안 JWKS에 남는다 — 그 키가 서명한 토큰이 유효할 수 있는 시간보다 길다. 키스토어는 원자적으로 쓰이는 JSON 파일이다; 기존 32바이트 시드 파일도 로드되며 첫 저장 시 마이그레이션된다. 오리진은 여전히 로컬에서 토큰을 검증하며, kid 클레임으로 키를 선택한다.

스토어: 멀티노드용 Redis (ADR-0009)

인메모리 스토어는 Mythic을 단일 노드에 묶었다. MYTHIC_STORE=redis는 Redis 백엔드를 선택한다: single-use 챌린지는 GETDEL(원자적 조회-삭제), 압력 카운터는 하나의 Lua 스크립트로 프룬되는 정렬 집합. 두 백엔드 모두 슬라이딩 윈도우 카운터를 구현해 고정 윈도우 경계 버스트를 닫았다. Store 인터페이스는 이제 오류를 반환한다: 도달할 수 없는 Redis는 시작을 거부하고, 런타임 장애는 /v1에서 503 store_unavailable으로 나타난다 — /healthz는 로드 밸런서를 위해 열려 있다. 공유 계약 스위트가 두 백엔드(memory와 miniredis) 모두를 실행해 시맨틱이 어긋날 수 없게 한다.

한 가지는 서면으로 밝힌다: 스토어는 공유되지만 서명 키는 공유되지 않는다. 노드 A의 토큰은 노드 B의 JWKS로 검증되지 않는다. 멀티노드 토큰 검증에는 공유 키스토어(KMS/HSM)가 필요하다 — M5이며, 이 변경으로 해결되지 않았다.

하드닝 패스: 12건의 발견

어버서럴 테스트 — 살아있는 서버 대상 블랙박스, 필요시 화이트박스 확인 — 가 12건의 발견을 냈다. 주요 것들을 영역별로:

전송과 제한

레이트 제한 예산은 검증 후에만 소모됐다: invalid-JSON과 미등록 사이트 키 홍수는 무제한이었다(225 req/s로 600 요청, 429 제로). 예산은 이제 검증 전에 계산된다. 리미터는 IPv6를 /128로 키잉했다 — 하나의 /64가 2⁶⁴ 정체성을 장악했다(블록 하나에서 5,000 요청, 히트 제로); 카운터는 이제 IPv6를 /64로 집계한다 (ADR-0007). 바디/읽기/유휴 타임아웃이 없었다; 느린 클라이언트가 연결을 무기한 붙잡을 수 있었다. ReadTimeout, WriteTimeout, IdleTimeout이 설정됐다.

챌린지 경제성

풀이 시간 플로어는 5만 H/s 워커를 가정했다; 실측 crypto.subtle 워커는 약 40만 H/s여서 정직한 클라이언트가 부적합으로 표시됐다 — 그리고 어떤 클라이언트든 검증을 플로어 너머까지 지연시키기만 하면 됐다. 플로어는 이제 정직한 풀이 시간의 낮은 분위수다 (2^d / (2M × 32), ADR-0008): 위양성은 최악 ~6%, GPU급 답변은 ~96%에서 걸린다. 스레드 모델은 실제 시간 플로어가 검증을 지연시키는 클라이언트는 잡을 수 없다는 점 — 그것은 행동 레이어(M2)의 일 — 을 명시한다.

토큰과 설정

토큰이 챌린지보다 오래 살지 않는다는 문서화된 불변식은 강제되지 않았다 — 5초짜리 챌린지에서 1시간짜리 토큰이 발행됐다. TokenTTL은 이제 ChallengeTTL로 클램프된다. 적대적 튜닝(MYTHIC_FAST_SOLVE_PENALTY=500)이 서명된 토큰에 500의 리스크 점수를 누출했다; 점수는 0–100으로 클램프되고 100을 넘는 페널티는 시작을 거부한다. 음수 MYTHIC_BASE_DIFFICULTY는 아무 nonce나 통과하는 챌린지를 발행했다; 설정은 시작 시 검증되고 범위를 벗어난 값은 서비스를 거부한다.

상태 처리

하나의 키스토어를 공유하는 두 프로세스는 같은 임시 파일에서 충돌하거나 조용히 서명 키를 스플릿브레인했다; 임시 이름은 프로세스별로 유일해지고 저장은 로드 후 변경된 파일의 덮어쓰기를 거부한다. JSON 값 뒤의 남은 바이트는 조용히 무시됐다; 이제는 거부된다. 슬라이딩 윈도우 카운터는 히트마다 하나의 엔트리를 저장했다 — 레이트 제한된 것 포함 — 그래서 단일 정체성의 백만 히트는 약 16.4 MB의 힙과 595초의 CPU를 요구했다. 카운터는 이제 IPLimit+1에서 포화된다: 같은 홍수의 비용은 +0.00 MB와 714 ms.

검증

모든 발견에는 재현 절차가 있고, 모든 수정에는 회귀 테스트가 있다 (go test ./... -race, SDK 타입체크와 테스트 포함), 그리고 모든 수정은 원래 재현 절차로 재검증되었다. 남아있는 항목은 스레드 모델에 문서화되어 있다: 검증을 지연시키는 인내심 있는 솔버(M2, 행동 신호), 새 정체성을 가진 분산 공격(M1, 네트워크 핑거프린트), 노드별 키스토어(M5, 공유 KMS/HSM).
